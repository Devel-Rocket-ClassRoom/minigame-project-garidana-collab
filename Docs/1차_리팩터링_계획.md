# 1차 리팩터링 계획

> 작성일: 2026-06-10  
> 대상 프로젝트: 김경일의 모험 : Origin (Unity 6.3 / 액션 RPG)  
> 상태: **계획 단계** — 실제 작업 전 검토 필요

---

## 개요

코드베이스 전체를 검토한 결과 6개의 리팩터링 항목을 도출했다.  
현재 기능 동작에는 문제가 없지만, 유지보수성과 확장성 측면에서 개선이 필요한 영역이다.  
항목별로 적용할 디자인 패턴과 구체적인 변경 방향을 기술한다.

## 항목별 상세

### [R-01] BaseMonster / BossMonster 코드 중복 제거

**패턴:** Template Method  
**우선순위:** ★★★★★ (가장 높음)  
**관련 파일:**
- `Assets/Scripts/Monster/BaseMonster.cs`
- `Assets/Scripts/Monster/BossMonster.cs`

#### 문제

두 클래스에 완전히 동일한 코드가 복사되어 있다.  
한쪽에서 버그를 수정해도 다른 쪽은 자동으로 반영되지 않는다.

| 메서드 | 상태 |
|--------|------|
| `PlayHitEffect()` | 두 파일 100% 동일 |
| `SinkAndDestroy()` 코루틴 | 두 파일 100% 동일 |
| `TakeDamage()` / `TakeHit()` | 구조 거의 동일 |
| `ProcessDrop()` | 부분 중복 |
| `Die()` | 유사 구조 |

#### 변경 방향

`BossMonster`가 `BaseMonster`를 상속하도록 변경한다.

```
AbstractMonster (또는 기존 BaseMonster 확장)
├── BaseMonster   — 일반 몬스터 (패트롤 / 추적 / 공격)
└── BossMonster   — 보스 고유 로직만 override
```

- `PlayHitEffect()`, `SinkAndDestroy()`는 기반 클래스로 올림
- `Die()`, `ProcessDrop()`은 `virtual`로 선언, 보스에서 `override`
- `TakeHit()`은 기반 클래스에서 공통 처리 후 `OnTakeHit()` 훅 메서드로 분기

#### 기대 효과

- 중복 코드 약 150줄 제거
- 이후 몬스터 종류 추가 시 기반 클래스 한 곳만 수정

### [R-02] EquipmentManager switch/case 반복 제거

**패턴:** Data-Driven (Dictionary 슬롯 구조)  
**우선순위:** ★★★★☆  
**관련 파일:**
- `Assets/Scripts/Player/EquipmentManager.cs`

#### 문제

`EquipmentPart` 5개에 대한 switch/case가 4개 메서드에 각각 반복된다.  
장비 부위(예: 반지, 목걸이 등)를 추가할 때 4~5군데를 모두 수정해야 한다.

```csharp
// 현재 — 동일한 switch/case가 4개 메서드에 반복됨
switch (data.equipmentPart)
{
    case EquipmentPart.Sword:   ...
    case EquipmentPart.Shield:  ...
    case EquipmentPart.Helmet:  ...
    case EquipmentPart.Chest:   ...
    case EquipmentPart.Legs:    ...
}
```

#### 변경 방향

`EquipmentSlot` 구조체와 `Dictionary<EquipmentPart, EquipmentSlot>`으로 교체한다.

```csharp
private struct EquipmentSlot
{
    public ItemData equippedItem;
    public Transform mountParent;
}

private Dictionary<EquipmentPart, EquipmentSlot> _slots;
```

- `EquipItem()`, `UnequipItem()`, `GetEquippedItem()`, `GetMountParent()` 모두 딕셔너리 조회로 단순화
- 부위 추가 시 딕셔너리 초기화 한 곳만 수정

#### 기대 효과

- 코드량 약 40% 감소
- 부위 추가/삭제 시 단일 지점 수정

### [R-03] PlayerStats 레벨업 공식 하드코딩 제거

**패턴:** ScriptableObject Configuration  
**우선순위:** ★★★★☆  
**관련 파일:**
- `Assets/Scripts/Player/PlayerStats.cs`

#### 문제

레벨업 공식이 `LevelUp()`과 `RestoreProgress()` 두 곳에 나뉘어 하드코딩되어 있다.  
둘 중 하나만 수정하면 공식 불일치 버그가 발생한다.

```csharp
// LevelUp() 에서
_expToLevelUp += 20;
IncreaseAttackPower(1f);
IncreaseMaxHealth(5f);

// RestoreProgress() 에서 — 같은 공식을 다시 계산
_attackPower  = _baseAttackPower + (_level - 1);        // 1f 단위
_maxHealth    = _baseMaxHealth + ((_level - 1) * 5f);   // 5f 단위
_expToLevelUp = 100 + ((_level - 1) * 20);              // 20 단위
```

#### 변경 방향

`PlayerLevelConfig` ScriptableObject를 만들어 공식을 외부화한다.

```csharp
[CreateAssetMenu]
public class PlayerLevelConfig : ScriptableObject
{
    public int baseExp = 100;
    public int expIncreasePerLevel = 20;
    public float attackIncreasePerLevel = 1f;
    public float healthIncreasePerLevel = 5f;

    public int GetExpToLevelUp(int level)  => baseExp + (level - 1) * expIncreasePerLevel;
    public float GetAttackBonus(int level) => (level - 1) * attackIncreasePerLevel;
    public float GetHealthBonus(int level) => (level - 1) * healthIncreasePerLevel;
}
```

- `LevelUp()`과 `RestoreProgress()` 모두 이 SO를 참조
- 밸런스 조정 시 에디터에서 수치만 변경하면 즉시 반영

#### 기대 효과

- 공식 불일치 버그 원천 차단
- 기획자(비개발자)도 에디터에서 밸런스 수치 수정 가능

### [R-04] SaveManager의 FindFirstObjectByType 의존성 제거

**패턴:** Service Registration (컴포넌트 자기 등록)  
**우선순위:** ★★★☆☆  
**관련 파일:**
- `Assets/Scripts/Managers/SaveManager.cs`

#### 문제

`CaptureCurrentState()`와 `ApplyLoadedStateNextFrame()` 양쪽에서 동일한 6개 컴포넌트를 씬 전체 탐색으로 가져온다.

```csharp
// 저장 시와 로드 시 모두 씬 탐색 반복
PlayerStats      playerStats      = FindFirstObjectByType<PlayerStats>();
PlayerHealing    playerHealing    = FindFirstObjectByType<PlayerHealing>();
PlayerInventory  playerInventory  = FindFirstObjectByType<PlayerInventory>();
EquipmentManager equipmentManager = FindFirstObjectByType<EquipmentManager>();
QuestManager     questManager     = QuestManager.Instance;

```

#### 변경 방향

각 컴포넌트의 `OnEnable` / `OnDisable`에서 SaveManager에 자신을 등록/해제한다.

```csharp
// PlayerStats.cs
private void OnEnable()  => SaveManager.Instance?.Register(this);
private void OnDisable() => SaveManager.Instance?.Unregister(this);
```

- SaveManager는 등록된 참조를 직접 사용 (씬 탐색 불필요)
- 컴포넌트가 없는 씬에서 저장 시도 시 명확한 에러 발생

#### 기대 효과

- 씬 탐색 비용 제거
- 씬 구조 변경에 덜 취약한 구조

### [R-05] Singleton 구현 방식 통일

**패턴:** Generic MonoSingleton\<T\>  
**우선순위:** ★★☆☆☆ (기술 부채, 기능 영향 없음)  
**관련 파일:**
- `Assets/Scripts/Sound/SoundManager.cs`
- `Assets/Scripts/Managers/SaveManager.cs`
- `Assets/Scripts/Quest/QuestManager.cs`
- `Assets/Scripts/Waypoint/WaypointManager.cs`
- `Assets/Scripts/Managers/HitStopManager.cs`

#### 문제

Singleton 보일러플레이트가 각 클래스마다 다르게 구현되어 있다.

| 클래스 | 초기화 방식 |
|--------|------------|
| `SoundManager` | `RuntimeInitializeOnLoadMethod` + DontDestroyOnLoad |
| `SaveManager` | `RuntimeInitializeOnLoadMethod` + DontDestroyOnLoad |
| `QuestManager` | `Awake()`에서 `Instance = this` (씬 로컬) |
| `WaypointManager` | `Awake()`에서 `Instance = this` (씬 로컬) |

#### 변경 방향

```csharp
public abstract class MonoSingleton<T> : MonoBehaviour where T : MonoBehaviour
{
    public static T Instance { get; private set; }

    protected virtual bool PersistAcrossScenes => false;

    protected virtual void Awake()
    {
        if (Instance != null && Instance != this)
        {
            Destroy(gameObject);
            return;
        }
        Instance = this as T;
        if (PersistAcrossScenes) DontDestroyOnLoad(gameObject);
    }
}
```

- `SoundManager`, `SaveManager` → `PersistAcrossScenes = true` override
- `QuestManager`, `WaypointManager` → 기본값(false) 사용

#### 기대 효과

- Singleton 보일러플레이트 코드 제거
- 새 매니저 추가 시 일관된 패턴 적용

### [R-06] BossMonster 패턴 AI 구조 개선

**패턴:** State Machine  
**우선순위:** ★★☆☆☆ (패턴 추가 시 필요)  
**관련 파일:**
- `Assets/Scripts/Monster/BossMonster.cs`

#### 문제

`Update()`에서 `patternRunning` 플래그를 확인한 뒤 코루틴을 시작하는데,  
`patternRunning = true` 세팅이 코루틴 내부 첫 줄에서 이루어진다.  
이론상 같은 프레임에 `PatternRoutine()`이 두 번 시작될 수 있는 구조다.  
또한 전투 상태, 패턴 실행, 사망 등의 전환 조건이 `Update()`에 흩어져 있어 확장이 어렵다.

```csharp
// 현재 — Update에서 매 프레임 코루틴 시작 여부 판단
private void Update()
{
    if (isDead || !combatStarted || patternRunning || ...) return;
    FacePlayer();
    StartCoroutine(PatternRoutine()); // patternRunning은 여기서 아직 false
}

private IEnumerator PatternRoutine()
{
    patternRunning = true; // 이 줄 이전에 Update가 한 번 더 실행될 수 있음
    ...
}
```

#### 변경 방향

```csharp
private enum BossState { Spawning, Idle, FacingPlayer, ExecutingPattern, Dead }
private BossState _currentState = BossState.Spawning;
```

- `Update()`는 현재 상태만 확인 후 상태별 메서드 호출
- 상태 전환은 `TransitionTo(BossState nextState)` 단일 메서드로 처리
- 패턴 추가/삭제 시 `PatternRoutine()` 내 switch와 `BossAttackType` enum만 수정

#### 기대 효과

- 중복 실행 버그 구조적 차단
- 패턴 추가 시 변경 지점 명확화

## 작업 순서 제안

```
R-01 (BaseMonster 통합)
  └─ R-02 (EquipmentManager 슬롯 구조)
       └─ R-03 (PlayerStats Config SO)
            └─ R-04 (SaveManager Registration)
                 └─ R-05 (Singleton 기반 클래스)
                      └─ R-06 (BossMonster State Machine)
```

R-01 → R-02 → R-03 순서로 진행 권장.  
R-04, R-05, R-06은 독립적으로 진행 가능.
