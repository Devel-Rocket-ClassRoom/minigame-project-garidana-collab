# 2차 리팩터링 계획

> 작성일: 2026-06-12  
> 대상 프로젝트: 김경일의 모험 : Origin (Unity 6.3 / 액션 RPG)  
> 문서 성격: 설계 검토 및 단계별 개선 계획  
> 상태: **계획 단계** - 실제 작업 전 항목별 영향 범위 확인 필요

---

## 1. 문서 목적

1차 리팩터링 계획에서 발견한 중복 코드와 하드코딩 문제를 바탕으로, 이번 계획에서는 프로젝트의 구조적 책임을 더 명확하게 나누는 것을 목표로 한다.

단순히 디자인 패턴의 개수를 늘리는 것이 아니라 다음 기준으로 패턴을 선택한다.

- 변경 이유가 다른 코드를 분리할 수 있는가
- 현재 반복되는 조건문과 탐색 코드를 줄일 수 있는가
- Unity의 씬, 프리팹, ScriptableObject 구조와 자연스럽게 결합되는가
- 기능을 유지하면서 작은 단계로 적용하고 검증할 수 있는가
- 향후 콘텐츠 확장 시 실제 수정 지점을 줄일 수 있는가

이 문서는 리팩터링의 기술적 근거, 적용할 패턴, 예상 구조, 검증 기준을 함께 기록하여 포트폴리오에서 설계 판단 과정을 설명할 수 있도록 구성한다.

---

## 2. 현재 구조 진단

현재 프로젝트는 기능 단위 구현과 C# 이벤트 기반 연결이 비교적 명확하지만, 일부 클래스에 책임이 집중되어 있다.

| 영역 | 현재 상태 | 주요 위험 |
|---|---|---|
| `SaveManager` | 저장, 복원, 탐색, 암호화, 레지스트리 구축을 한 클래스가 담당 | 변경 영향 범위가 넓고 테스트가 어려움 |
| `BaseMonster` / `BossMonster` | 피격, 사망, 보상, 이펙트 코드가 중복 | 버그 수정 누락 가능 |
| `PlayerStats` | 기본 능력치, 레벨 성장, 장비 증감이 동일 필드를 직접 변경 | 복원 및 장착 순서에 따라 값이 달라질 수 있음 |
| `EquipmentManager` | 장비 부위별 필드와 `switch` 반복 | 부위 추가 시 여러 파일 동시 수정 |
| `InventoryUi` | 입력, 데이터 분류, 슬롯 생성, 화면 표시가 한 클래스에 집중 | UI 변경과 게임 규칙 변경이 서로 영향 |
| `PlayerInteractor` | 여러 UI의 static 상태를 직접 확인 | 새 UI 추가 시 플레이어 코드 수정 필요 |
| 시간 제어 | `PauseManager`, `HitStopManager`가 각각 `Time.timeScale` 변경 | 중첩 요청 시 잘못된 시간 복원 가능 |
| 전투 및 UI 효과 | 여러 클래스에서 `Instantiate` / `Destroy` 반복 | 생성 코드 중복 및 런타임 할당 증가 |
| 데이터 조회 | 저장 시 아이템과 퀘스트를 런타임 탐색으로 수집 | 누락 및 중복 ID를 사전에 검증하기 어려움 |

## 3. 설계 원칙

### 3.1 단일 책임 원칙

클래스는 하나의 변경 이유를 갖도록 분리한다.

- 저장 흐름과 암호화 방식은 서로 다른 책임이다.
- 몬스터의 공통 전투 생명주기와 개별 AI는 서로 다른 책임이다.
- UI 렌더링과 구매 또는 장착 규칙은 서로 다른 책임이다.

### 3.2 개방-폐쇄 원칙

새 콘텐츠를 추가할 때 기존 조건문을 계속 수정하기보다 데이터나 구현체를 추가할 수 있는 구조를 지향한다.

- 장비 부위 정의를 Registry로 관리
- 보스 공격 선택을 Strategy로 확장
- 저장 인코딩 방식을 Strategy로 교체

### 3.3 의존성 역전 원칙

상위 흐름이 구체적인 Unity 탐색 및 파일 처리 구현에 직접 의존하지 않도록 경계를 만든다.

- `SaveManager`는 파일 암호화 세부 구현보다 저장 인터페이스에 의존
- Presenter는 Unity UI 컴포넌트보다 View 계약에 의존
- 효과 사용자는 직접 생성 방식보다 효과 생성 서비스에 의존

### 3.4 데이터와 런타임 상태 분리

ScriptableObject에는 공유 설정만 보관하고 개별 플레이 상태는 MonoBehaviour 또는 별도 런타임 객체에 보관한다.

- `ItemData`, `MonsterData`, `QuestData`: 공유 정의
- 현재 체력, 장착 여부, 퀘스트 진행량: 개별 상태

### 3.5 점진적 적용

패턴 적용 자체를 목표로 삼지 않는다. 각 항목은 기존 동작을 유지하는 작은 변경 단위로 진행한다.

### [R2-01] 플레이어 능력치 계산 구조 개선

**적용 패턴:** Composition + Configuration  
**우선순위:** 최상  
**관련 파일:**

- `Assets/Scripts/Player/PlayerStats.cs`
- `Assets/Scripts/Player/EquipmentManager.cs`
- 신규 `PlayerLevelConfig.cs`

#### 문제

현재 `PlayerStats`의 공격력과 최대 체력은 레벨업 및 장비 장착 과정에서 직접 더하고 뺀다.

```text
LevelUp()          -> 공격력과 최대 체력 증가
EquipmentManager  -> 장착 시 증가, 해제 시 감소
RestoreProgress() -> 레벨 기준으로 필드 재계산
```

이 구조에서는 호출 순서나 중복 호출에 따라 누적 값이 잘못될 가능성이 있다.

#### 변경 방향

최종 능력치를 여러 독립 구성 요소의 합으로 계산한다.

```text
최종 공격력
= 기본 공격력
+ 레벨 성장 보너스
+ 장비 보너스
+ 향후 임시 효과
```

```csharp
public float AttackPower =>
    _baseAttackPower
    + _levelAttackBonus
    + _equipmentAttackBonus;
```

레벨 성장 공식은 `PlayerLevelConfig` ScriptableObject로 외부화한다.

#### 적용 효과

- 레벨 복원과 장비 복원 순서에 덜 민감해진다.
- 장착과 해제에서 음수 값을 전달하는 방식이 제거된다.
- 버프, 디버프, 난이도 보정 추가가 쉬워진다.
- 밸런스 수치를 코드 수정 없이 조정할 수 있다.

#### 검증 기준

- 동일 레벨과 동일 장비에서 실행 순서와 무관하게 최종 능력치가 동일해야 한다.
- 저장 후 로드했을 때 공격력과 최대 체력이 저장 전과 같아야 한다.
- 장비를 반복 장착 및 해제해도 능력치 오차가 누적되지 않아야 한다.

### [R2-02] 장비 슬롯을 데이터 기반 Registry로 전환

**적용 패턴:** Registry + Data-Driven Design  
**우선순위:** 높음  
**관련 파일:**

- `Assets/Scripts/Player/EquipmentManager.cs`
- `Assets/Scripts/UI/InventoryUi.cs`
- `Assets/Scripts/Managers/SaveManager.cs`
- `Assets/Scripts/ScriptableObjects/ItemData.cs`

#### 문제

장비 부위별 필드와 `switch`가 반복되며 저장 데이터와 UI도 5개 부위에 고정되어 있다.

#### 변경 방향

Inspector에 노출되는 슬롯 정의와 런타임 상태를 분리한다.

```csharp
[Serializable]
public class EquipmentSlotDefinition
{
    public EquipmentPart part;
    public Transform mountParent;
    public ItemData defaultItem;
}
```

```text
List<EquipmentSlotDefinition>
        |
        v
Dictionary<EquipmentPart, EquipmentSlotState>
```

값 변경이 필요한 런타임 슬롯은 가변 `struct`보다 참조 타입 또는 명시적인 갱신 메서드를 사용한다.

#### 단계 구분

1. 현재 5개 부위의 `EquipmentManager` 중복 제거
2. 저장 데이터를 부위와 아이템 ID의 목록 구조로 변경
3. `InventoryUi`의 행과 아이콘 구성을 슬롯 정의 기반으로 변경
4. 기존 세이브 버전 마이그레이션 처리

#### 적용 효과

- 장비 부위별 반복 코드 감소
- 장비 부위 확장 지점 명확화
- 기본 장비, 마운트 위치, 현재 장착 상태의 역할 분리

#### 검증 기준

- 기본 장비 지급 및 장착이 기존과 동일해야 한다.
- 장착, 교체, 해제 시 모델과 능력치가 정확히 반영되어야 한다.
- 기존 세이브 데이터의 장비가 정상 복원되어야 한다.

### [R2-03] SaveManager를 저장 Facade로 재구성

**적용 패턴:** Facade + Strategy + Handler  
**우선순위:** 최상  
**관련 파일:**

- `Assets/Scripts/Managers/SaveManager.cs`
- 신규 저장 관련 클래스

#### 문제

`SaveManager`는 1,000줄 이상이며 다음 책임을 동시에 수행한다.

- 저장 및 로드 흐름 제어
- 파일 입출력
- 암호화와 복호화
- 저장 대상 탐색
- 도메인별 상태 캡처 및 복원
- 아이템과 퀘스트 레지스트리 구축
- 구버전 세이브 호환

#### 목표 구조

```text
SaveManager (Facade)
├── SaveFileStorage
├── ISaveCodec
│   ├── EncryptedJsonSaveCodec
│   └── PlainJsonLegacyCodec
├── PlayerSaveHandler
├── EquipmentSaveHandler
├── QuestSaveHandler
└── WorldSaveHandler
```

외부에서는 기존처럼 단순한 API만 사용한다.

```csharp
SaveManager.Instance.SaveGame();
```

암호화와 직렬화 방식은 Strategy로 분리한다.

```csharp
public interface ISaveCodec
{
    string Encode(SaveData data);
    bool TryDecode(string text, out SaveData data);
}
```

#### 적용 효과

- 암호화 수정이 게임 상태 캡처 코드에 영향을 주지 않는다.
- 저장 도메인별 코드를 독립적으로 검증할 수 있다.
- 기존 평문 세이브 호환 로직을 별도 구현으로 격리할 수 있다.
- `SaveManager`는 저장 순서를 조율하는 Facade 역할에 집중한다.

#### 검증 기준

- 기존 암호화 세이브를 정상적으로 읽을 수 있어야 한다.
- 기존 평문 세이브를 읽고 다음 저장 시 암호화 형식으로 전환해야 한다.
- 손상되거나 변조된 세이브를 안전하게 거부해야 한다.
- 플레이어, 장비, 퀘스트, 웨이포인트, 상인, 상자 상태가 모두 복원되어야 한다.

### [R2-04] 아이템 및 퀘스트 데이터 Registry 구축

**적용 패턴:** Registry + Flyweight 유지  
**우선순위:** 높음  
**관련 파일:**

- `Assets/Scripts/ScriptableObjects/ItemData.cs`
- `Assets/Scripts/ScriptableObjects/QuestData.cs`
- `Assets/Scripts/Managers/SaveManager.cs`
- 신규 `ItemRegistry.cs`
- 신규 `QuestRegistry.cs`

#### 문제

저장 로드 과정에서 `Resources.FindObjectsOfTypeAll`과 씬 오브젝트 탐색을 통해 데이터 목록을 구축한다.

#### 변경 방향

프로젝트에서 사용하는 공유 데이터를 명시적으로 등록하는 ScriptableObject Registry를 만든다.

```csharp
[CreateAssetMenu]
public class ItemRegistry : ScriptableObject
{
    [SerializeField] private List<ItemData> items;

    public bool TryGet(string itemId, out ItemData item);
}
```

`ItemData`, `QuestData`, `MonsterData`, `SoundData`는 기존처럼 공유 데이터를 제공하는 Flyweight 역할을 유지한다. 소유 여부나 진행 상태 같은 런타임 값은 저장하지 않는다.

#### 적용 효과

- 런타임 전체 탐색 감소
- 중복 ID와 누락 ID를 에디터 검증으로 발견 가능
- 저장 시스템이 상인과 상자를 데이터 검색 목적으로 탐색할 필요 감소
- 저장 ID와 ScriptableObject 참조의 변환 경로가 명확해짐

#### 검증 기준

- Registry 내 중복 ID가 검출되어야 한다.
- 저장된 모든 아이템 및 퀘스트 ID를 복원할 수 있어야 한다.
- Registry에 없는 ID가 들어왔을 때 명확한 경고를 출력하고 로드를 계속할 수 있어야 한다.

### [R2-05] 몬스터 전투 생명주기 공통화

**적용 패턴:** Template Method  
**우선순위:** 높음  
**관련 파일:**

- `Assets/Scripts/Monster/BaseMonster.cs`
- `Assets/Scripts/Monster/BossMonster.cs`
- `Assets/Scripts/Monster/MonsterHpBar.cs`
- 신규 `MonsterCombatBase.cs`

#### 문제

일반 몬스터와 보스는 피격, 체력 이벤트, 사망, 보상, 퀘스트 보고, 이펙트, 제거 연출을 중복 구현한다.

`BossMonster`가 현재 `BaseMonster`를 직접 상속하는 방식은 적합하지 않다. `BaseMonster`에는 순찰, 추적, 공격, 넉백 등 일반 몬스터 전용 동작이 포함되어 있기 때문이다.

#### 변경 방향

공통 전투 생명주기만 `MonsterCombatBase`로 추출한다.

```text
MonsterCombatBase
├── BaseMonster : 일반 몬스터 AI
└── BossMonster : 보스 패턴 AI
```

Template Method가 담당할 흐름:

```text
피격 가능 여부 확인
-> 체력 감소
-> 체력 변경 이벤트
-> 공통 피격 효과
-> 개별 피격 훅
-> 사망 판정
-> 공통 사망 처리
-> 개별 사망 훅
-> 보상 및 퀘스트 처리
-> 제거 연출
```

개별 클래스는 다음 훅만 구현한다.

```csharp
protected virtual void OnHitTaken(DamageHitInfo hitInfo) { }
protected virtual void OnDeathStarted() { }
```

#### 적용 효과

- 피격 및 사망 버그를 한 곳에서 수정할 수 있다.
- `MonsterHpBar`가 일반 몬스터와 보스를 별도로 처리하지 않아도 된다.
- 향후 원거리 몬스터와 엘리트 몬스터 추가 기반이 마련된다.

#### 검증 기준

- 일반 몬스터의 넉백, 드롭, 퀘스트 아이템 생성이 유지되어야 한다.
- 보스의 페이즈 전환, 소환수 정리, 사망 이벤트가 유지되어야 한다.
- 모든 몬스터의 체력바와 이름 표시가 정상 동작해야 한다.

### [R2-06] 보스 전투 흐름 명시화

**적용 패턴:** State + Strategy  
**우선순위:** 중간  
**관련 파일:**

- `Assets/Scripts/Monster/BossMonster.cs`
- 신규 보스 상태 또는 패턴 관련 클래스

#### 문제

보스의 상태가 여러 bool 조합으로 표현된다.

```text
isDead
combatStarted
patternRunning
phaseTwoStarted
spawnStarted
summonReserved
```

현재 `StartCoroutine()` 호출 직후 코루틴이 첫 `yield`까지 실행되므로 `patternRunning` 중복 실행이 핵심 문제는 아니다. 실제 개선 목적은 상태 전환과 패턴 확장 지점을 명확하게 만드는 것이다.

#### 변경 방향

초기에는 enum 기반 상태 머신으로 단순화한다.

```text
Dormant
-> Spawning
-> Waiting
-> ExecutingPattern
-> PhaseTransition
-> Dead
```

State는 보스가 현재 무엇을 하는지 담당한다. Strategy는 어떤 공격을 선택하고 실행할지 담당한다.

```csharp
public interface IBossAttackStrategy
{
    bool CanExecute(BossCombatContext context);
    IEnumerator Execute(BossCombatContext context);
}
```

공격 종류나 보스 종류가 늘기 전에는 모든 공격을 즉시 클래스로 분리하지 않는다. 우선 `BossPatternSelector`와 상태 전환만 분리하고 확장 필요가 확인될 때 개별 Strategy로 발전시킨다.

#### 적용 효과

- 등장, 공격, 페이즈 전환, 사망의 전환 조건이 명확해진다.
- 실행 중 패턴 취소와 사망 처리를 안전하게 구현할 수 있다.
- 새로운 보스 패턴을 추가할 때 기존 상태 흐름 수정이 줄어든다.

#### 검증 기준

- 보스 등장 연출이 끝나기 전에 공격하지 않아야 한다.
- 사망 후 실행 중인 패턴과 소환이 중단되어야 한다.
- 2페이즈 진입과 소환 패턴이 한 번만 실행되어야 한다.
- 같은 공격의 반복 방지 규칙이 유지되어야 한다.

### [R2-08] 시간 배율 제어 통합

**적용 패턴:** Mediator  
**우선순위:** 높음  
**관련 파일:**

- `Assets/Scripts/Managers/PauseManager.cs`
- `Assets/Scripts/Managers/HitStopManager.cs`
- 신규 `TimeScaleController.cs`

#### 문제

`PauseManager`와 `HitStopManager`가 각각 `Time.timeScale`과 `Time.fixedDeltaTime`을 직접 변경한다.

히트 스톱 도중 일시정지를 하거나 일시정지 중 히트 스톱 요청이 발생하면, 한 시스템이 다른 시스템의 배율을 잘못 복원할 수 있다.

#### 변경 방향

각 기능은 시간 배율을 직접 변경하지 않고 요청만 등록한다.

```text
PauseManager -----\
                   > TimeScaleController -> Time.timeScale
HitStopManager ---/
```

최종 시간 배율 정책:

```text
Pause 요청이 있으면 0
그 외 HitStop 요청이 있으면 활성 요청 중 가장 낮은 값
요청이 없으면 기본 배율 1
```

#### 적용 효과

- 시간 관련 기능의 소유권이 한 곳으로 모인다.
- 일시정지와 히트 스톱 중첩을 안전하게 처리할 수 있다.
- 슬로 모션과 컷신 배율 같은 기능을 같은 방식으로 확장할 수 있다.

#### 검증 기준

- 히트 스톱 종료 후 기존 시간 상태로 정확히 복귀해야 한다.
- 일시정지 중에는 히트 스톱 종료가 게임을 재개시키지 않아야 한다.
- `Time.fixedDeltaTime`이 최종 배율과 일관되게 갱신되어야 한다.

여러 클래스가 파티클과 플로팅 텍스트를 직접 생성하고 수명을 계산하여 제거한다.

- 일반 몬스터

- 씬에서 드물게 생성되는 UI

#### 적용 효과

- 효과 초기화와 수명 계산 중복 제거
- 풀링 도입 시 호출부 변경 최소화

#### 검증 기준

- 반환된 오브젝트의 이전 상태가 다음 사용에 남지 않아야 한다.
- 씬 전환 및 비활성화 시 풀이 잘못된 참조를 유지하지 않아야 한다.

## 5. 현재 도입하지 않는 패턴

패턴을 적용하지 않기로 한 판단도 설계의 일부로 기록한다.

### Monster Factory

현재 일반 몬스터는 씬 또는 프리팹에 배치되고, 보스와 소환수 생성도 단순한 `Instantiate` 중심이다.

Factory 도입 조건:

- 웨이브 시스템
- 지역별 스폰 테이블
- 난이도 및 레벨 보정
- 엘리트 변형 생성
- 몬스터 Object Pool
- 생성 후 공통 초기화 증가

현재는 보스 소환 책임을 `MinionSpawner`로 분리하는 정도가 적절하다.

### Command

현재 입력은 단순 소비 구조로 충분하다. 입력 버퍼링, 행동 기록 및 재생, AI와 플레이어 행동 공유가 필요할 때 도입한다.

### Chain of Responsibility

방어력, 치명타, 속성 저항, 보호막 등 대미지 수정 단계가 늘어날 때 도입한다. 현재는 `DamageHitInfo`를 확장 가능한 구조로 유지한다.

### Composite

현재 퀘스트는 단일 목표 구조로 충분하다. 하나의 퀘스트에 여러 목표가 필요해질 때 `CompositeObjective`를 검토한다.

### 전면적인 MVP

단순 HUD와 체력바까지 MVP로 분리하지 않는다. 화면 로직과 게임 규칙이 실제로 혼합된 대형 UI에만 제한적으로 적용한다.

### 모든 Manager의 Generic Singleton 통합

매니저마다 생명주기가 다르므로 하나의 기반 클래스로 무조건 통합하지 않는다.

```text
자동 생성 및 영구 유지: SaveManager, SoundManager, SceneLoader
씬 로컬: QuestManager, WaypointManager
요청 시 생성: PauseManager, HitStopManager
```

먼저 생명주기 정책을 정의하고 같은 정책끼리만 공통화한다.

## 7. 공통 검증 계획

### 정적 검증

- 새로 추가한 Registry의 중복 ID 검사
- Inspector 필수 참조 누락 검사
- 이벤트 구독과 해제 대칭 확인

- 새 게임 시작 및 기존 저장 로드
- 장비 장착, 교체, 해제 후 능력치 확인
- 일반 몬스터 피격, 넉백, 사망, 드롭

- 상인 재고와 상자 개봉 상태 저장 및 복원

### 회귀 방지 기준

- 세이브 데이터 형식이 바뀌면 `version`을 올리고 명시적인 마이그레이션을 제공한다.
- 리팩터링과 신규 콘텐츠 구현을 같은 변경에 섞지 않는다.

## 8. 기대 결과

이번 리팩터링을 완료하면 프로젝트는 다음 방향으로 개선된다.

- 능력치와 장비 계산이 호출 순서에 의존하지 않는다.
- 저장 시스템의 암호화, 파일 처리, 게임 상태 복원이 독립적으로 관리된다.
- 일반 몬스터와 보스가 공통 전투 규칙을 공유하면서 각자의 AI를 유지한다.
- UI가 서로의 구체 타입을 직접 확인하지 않고 중앙 정책을 통해 입력을 조정한다.
- 일시정지, 히트 스톱, 향후 슬로 모션이 충돌 없이 공존한다.
- 아이템과 퀘스트 ID의 유효성을 런타임 이전에 검증할 수 있다.
- 반복 생성되는 효과의 코드 중복과 런타임 할당을 줄일 수 있다.
- 패턴 추가 자체보다 변경 영향 범위를 줄였다는 점을 설명할 수 있는 구조가 된다.

## 9. 포트폴리오 관점의 핵심 설명

이 리팩터링의 핵심은 디자인 패턴을 나열하는 것이 아니라, 프로젝트에서 실제로 발생한 구조적 문제에 맞춰 패턴을 선택한 것이다.

- `SaveManager`의 책임 집중 문제에는 Facade와 Strategy를 적용한다.
- 몬스터 중복에는 직접 상속이 아니라 공통 생명주기만 추출한 Template Method를 적용한다.
- 플레이어 능력치에는 상속보다 Composition을 선택한다.
- UI와 시간 배율처럼 여러 시스템이 충돌하는 영역에는 Mediator를 적용한다.
- 공유 게임 데이터에는 Unity의 ScriptableObject를 활용하여 Flyweight 구조를 유지한다.
- 반복 생성 효과에는 Factory를 먼저 두고 실제 성능 필요가 있는 대상만 Object Pool로 발전시킨다.
- 보스의 상태와 공격 선택은 State와 Strategy의 역할을 구분한다.
- 현재 요구사항에 비해 과도한 Factory, Command, Composite 적용은 의도적으로 보류한다.

이를 통해 “어떤 패턴을 알고 있는가”보다 “왜 이 패턴을 이 위치에 선택했고, 왜 다른 위치에는 적용하지 않았는가”를 보여주는 것을 목표로 한다.
